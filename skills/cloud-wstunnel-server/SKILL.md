# 云环境私人服务部署

这是已验证可用的部署方案：云环境运行应用并主动建立 WSS 反向连接，VPS 提供中转，用户通过 Tailscale 访问应用。默认复用已有 VPS，为新云环境和新服务分配明确的内网端口映射。

访问链路：用户设备 → Tailscale → VPS 内网服务端口 → wstunnel → 云环境回环应用端口。

## 执行位置与授权

- 区分用户电脑、VPS 和托管云环境；在对应位置执行操作。本机工具不能直接操作另一云环境。
- 使用用户指定或明确授权的云对话，通过 `read_thread` 核实环境和应用，使用 `send_message_to_thread` 下发具体部署指令、`wait_threads` 跟踪结果。只有用户明确要求创建新对话时才使用创建对话工具；创建云环境遵循平台支持的配置流程，不拿旧对话冒充新环境。
- 读取当前云环境的 runtime 技能、`environment_status` 和支持的网络策略快照。新环境重新检查，不能继承旧实例的就绪结论。
- 云端只取得分配给该环境/服务的受限隧道凭证，不取得 VPS root 密码或 SSH 私钥。按已有授权继续；自动审批若要求具体凭证及目的地授权，说明理由并获取该项授权，同时完成其余准备。不将鉴权值写入 skill、报告或部署登记。

## 按现状选择入口

| 现状 | 执行范围 |
| --- | --- |
| 已有应用、VPS 中转可用 | 确认现有应用与隧道，直接新增受限映射 |
| 新云环境、已有 VPS | 检查新实例网络，部署应用和客户端，新增独立映射 |
| VPS 尚未部署中转 | 按 [deployment.md](references/deployment.md) 初始化有效 TLS、受限 WSS 中转及鉴权 |
| 替换/重建环境或原映射失效 | 按 [services.md](references/services.md) 的恢复流程重建应用与连接，处理旧映射和数据 |

## 标准部署流程

1. **复用中转。** 核实 VPS Tailscale 地址、WSS 入口、证书、现有监听和限制规则。保留已有映射，为新增服务选择空闲端口。只有缺失时才部署中转；详细参数见 [deployment.md](references/deployment.md)。
2. **验证当前云环境网络。** 保留继承的代理、平台 CA 和 TLS 校验，向实际 WSS 入口做有界请求。普通 HTTPS 返回 `400 Invalid request` 只是入口可达证据，后续还需实际转发。普通沙箱连接失败可通过工具支持的正常权限流程重试同一请求；明确策略拒绝须经支持的配置流程处理。
3. **部署或确认应用。** 用户已启动应用时，确认监听端口、健康状态和登录路径即可。新应用依照项目配置部署；Docker 遵循当前 runtime 的代理/CA规则，应用优先只发布到云端回环地址，数据库不作为默认转发目标。保留现有认证和数据，不为接入隧道而重建数据库或修改登录口令。
4. **分配受限映射。** 为服务登记云环境/对话、云端回环端口、VPS 内网绑定地址和外部端口。反向端口仅绑定 VPS Tailscale IPv4；服务端限制协议、绑定地址和批准端口。多环境使用独立凭证/限制条目，避免争用同一监听端口。更新配置时备份、原子替换，并核实热重载没有中断已有映射。
5. **由 Docker 管理独立客户端。** 应用转发默认使用独立 Compose 服务，`restart: unless-stopped`，通过 `docker compose up -d` 脱离工具会话运行；不再以工具运行会话或 `nohup` 承载持续转发。保留平台代理、只读 CA、TLS 验证和 SNI；容器网络必须实际能访问应用目标。按 [docker-client.md](references/docker-client.md) 部署与迁移，记录容器、Compose 路径和脱敏日志。已有健康转发若需持续运行，同样容器化；短时诊断才使用工具会话。
6. **验证用户入口。** 从用户设备请求 VPS 内网端口，检查实际页面/接口、登录跳转、表单及资源 URL。对已有认证应用，未登录首页跳转至登录页可以是正确行为；不将 302 一概判为失败。认证后的功能验证按授权执行，不为了证明隧道可用读取口令或业务数据。细节见 [services.md](references/services.md)。
7. **交付与登记。** 提供可点击的 Tailscale 内网 URL、端口映射、认证来源、容器/Compose 和日志位置、停止与恢复方式。记录答复结束后实际访问结果。明确云环境替换时哪些需要重建，尤其是应用、隧道客户端和持久数据。

## 排障

| 证据 | 处理 |
| --- | --- |
| 沙箱无法连接代理，正常升级后成功 | 使用支持的执行路径继续，不判定为外网不可用 |
| `vpn_configured=true`，实际返回 `VPN is not configured` | 快照不证明 VPN 就绪；复查状态并做同代理公共网站对照 |
| VPS 和普通公共网站都返回代理 503 | 停止重复修改中转；由平台支持入口处理实例出口。用户换云环境时独立重测 |
| 公共网站可访问，仅 VPS 失败 | 检查监听、DNS、TLS、代理目标和服务端日志 |
| HTTP 可达但隧道失败 | 检查 WSS 升级、客户端代理/CA及限制规则，不关闭证书验证 |
| 隧道通但应用不通 | 检查云端回环服务、Docker 端口发布、协议和 HTTP Host/跳转 |
| 应用和数据库正常，客户端进程/工具会话消失 | 检查日志末尾、会话及 OOM 证据；不猜测退出原因。迁移为 Docker 管理的客户端，配置自动重启并验证外部入口 |
| 容器 running，但入口不通 | 检查隧道握手、代理/CA、目标网络和限制；Docker 自动重启不等于隧道健康 |

禁止改写策略快照、清空云端代理、安装 executor 内 Tailscale 修复 sidecar，或用原始 TCP 代理绕行 HTTP 拒绝。不要重置整个 VPS、修改无关服务或清理他人的端口。

## 已验证实践与运行边界

2026-10-08 已完成两种真实部署：固定健康服务经隧道返回一致 boot_id；Docker 的 ai-fin 应用 `127.0.0.1:8688` 经 VPS Tailscale 内网端口 `19088` 访问，首页正确跳转、登录页 HTTP 200、资源可用，用户确认访问成功。原健康转发 `19082` 同时保留。

该方案已证明可部署并访问实际私人服务。平台暂停、环境重建、进程会话结束和证书到期仍需相应恢复/维护，不承诺平台提供永久在线资源。2026-10-09 用户反馈：两个工具会话中的客户端日志停在北京时间 01:32 左右，客户端退出而应用、数据库及邮箱转发容器仍运行；未发现 OOM 记录，具体触发原因未确定。因此后续默认容器化应用转发。Docker 自动重启策略改善进程退出恢复，但环境暂停/删除、守护进程不可用、网络故障与证书到期仍需恢复；隔夜及环境重建恢复必须实际验证后报告。

[scripts/health_server.py](scripts/health_server.py) 和 [scripts/probe.py](scripts/probe.py) 是可选的隧道诊断工具，不是部署每个应用的必经步骤。它们仅检查固定健康协议；验证应用使用实际页面/API。只有用户请求后续监测时才创建相应自动检查。
